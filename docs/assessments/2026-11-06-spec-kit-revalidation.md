# Spec Kit revalidation — Clinic platform

## Scope and method

This is a Spec Kit–informed requirements-quality and cross-artifact review of the approved clinic specification, the six existing implementation plans, and selected delivery evidence. The original requirements and approved specification remain authoritative; this report does not amend them. The independent specification review examined documents, not the installed backend or all application code. Findings below are not claims that planned write code has already been implemented.

Spec Kit 1.3.1 was initialized with the OpenCode integration and event hooks disabled. `specify integration status` reported OK, zero modified or missing managed files. Its generated constitution remains an unfilled template. The installed `speckit.analyze` command requires Spec Kit `spec.md`, `plan.md`, and `tasks.md` produced by its workflow; the existing project uses a different approved artifact layout. Therefore this report is **not** a formal `/speckit.analyze` or `/speckit.converge` result, and no convergence or acceptance pass is claimed. See [existing-project guidance](https://github.github.io/spec-kit/how-to/existing-projects.html) and [SDD command reference](https://github.github.io/spec-kit/reference/agentic-sdd.html).

## Verdict

**Not ready for P0 or live write activation.** The project has a detailed scope, default-deny write gates and a useful fixture-only implementation. However, material requirement/plan inconsistencies and incomplete verification remain. Fixture success, a review finding no issues in a limited scope, and installed-site or clinical acceptance are different kinds of evidence.

## Findings requiring resolution

1. **Patient identifiers in search URLs — requirements conflict.** Original NFR-04 prohibits patient identifiers in URL query parameters (`OpenDesign Requirements v3/Clinic_Functional_Requirements_v3.md:523`); the read plan sends `q` in an API GET query (`docs/superpowers/plans/2026-11-05-clinic-02-shell-shared-read.md:301-304`). A prior interim decision accepted API GET with log restrictions; that decision does not by itself reconcile the original NFR or prove absence from intermediary logs. Resolve with an explicit approved exception or a read-only POST contract, and verify browser/network requests and logging controls. Do not treat hiding text from the address bar as sufficient.
2. **Durable recovery lacks a concrete reconciliation path.** The approved spec requires write-ahead persistence, deterministic upstream reconciliation and real process-kill/restart evidence (`docs/superpowers/specs/2026-11-05-clinic-application-design.md:243-256`). The write plan says reconciliation reads only the log and never calls upstream while pending (`docs/superpowers/plans/2026-11-05-clinic-06-write-activation.md:159-169,215-217`); its restart example does not demonstrate an actual crash between upstream commit and local commit (`:233-250`). Specify recovery per operation and test both crash windows before activation.
3. **Operation-key scope and replay authorization conflict.** The spec defines `(user, operation, requestKey)` (`docs/superpowers/specs/2026-11-05-clinic-application-design.md:249`), but the write plan keys storage and several APIs by `requestKey` alone (`docs/superpowers/plans/2026-11-05-clinic-06-write-activation.md:43-50,82-84`). Resolve ownership, operation scope and reauthorization for replay/status; add cross-user, cross-operation and revoked-access tests.
4. **Booking payload is prematurely fixed.** The original requirements include appointment type and conditional resource, duration and service-unit fields (`OpenDesign Requirements v3/Clinic_Functional_Requirements_v3.md:316-324`). The write plan asserts an exact five-field payload (`docs/superpowers/plans/2026-11-05-clinic-06-write-activation.md:363-372`) before installed-site field verification. Make any fixture payload illustrative and derive actual requirements and allow-lists from the verified backend contract.
5. **Encounter creation/reuse and amendment need explicit executable coverage.** Original acceptance includes creation/reuse and permitted note amendment (`OpenDesign Requirements v3/Clinic_Functional_Requirements_v3.md:508,545,563`), while the current draft plan starts with an existing encounter and does not establish a complete amendment path (`docs/superpowers/plans/2026-11-05-clinic-06-write-activation.md:478-486,615-661`). Add explicit tasks, ownership and acceptance evidence, or mark these outcomes unplanned until agreed.
6. **Shared-workstation isolation needs measurable acceptance.** NFR-02 requires preventing shared-workstation disclosure (`OpenDesign Requirements v3/Clinic_Functional_Requirements_v3.md:521`). The planned query-key description (`docs/superpowers/plans/2026-11-05-clinic-02-shell-shared-read.md:303-308`) alone does not specify a full account-switch acceptance test. Require evidence for logout, another role logging in, browser Back, delayed responses, cached data and photo/draft cleanup. Current runtime protections need independent verification before making a defect claim.
7. **Acceptance evidence needs classes and provenance.** The planned matrix marks a row `pass` on a successful command plus an existing artifact (`docs/superpowers/plans/2026-11-05-clinic-06-write-activation.md:783-791`), but its automated harness is never pointed at a live site (`:816-818`). Distinguish fixture pass, installed-site contract verification, clinical UAT and production readiness; record environment, versions, assertions, reviewer/signature and evidence. Explicitly trace all required legacy surfaces and states rather than counting acceptance IDs alone.
8. **Expired inventory quantity semantics are contradictory.** Original requirements distinguish physical on-hand from usability for expired stock (`OpenDesign Requirements v3/Clinic_Functional_Requirements_v3.md:715-717`), while the project spec says expiry filters show usable positive on-hand (`docs/superpowers/specs/2026-11-05-clinic-application-design.md:507-508`). Define separate physical and usable quantities; include an expired batch with positive physical and zero usable stock in acceptance.

## Other gaps and constraints

- Clinical fixtures currently use identities isolated from front-desk fixtures. Cross-feature patient/appointment handoffs are not established (`.superpowers/sdd/2026-11-05-clinic-04-clinical-read/task-1-report.md`, review-fix section).
- The clinical read UI explicitly marks missing history fields, prior-record provenance, structured findings and note-composition evidence unavailable (`.superpowers/sdd/2026-11-05-clinic-04-clinical-read/task-3-report.md`, `task-4-report.md`). These are honest interim states, not proof of complete requirements.
- Photo Task 5 remains incomplete. Synthetic transport and router changes were in progress at audit time; they are not accepted by this report. Private file delivery, patient-scoped authorization, consent/revocation, metadata provenance and persisted annotation require their own verified contracts.
- Define measurable accessibility release criteria: automated thresholds plus human keyboard, assistive-technology and Thai-clipping sign-off at agreed viewport/device combinations. Existing Chromium fixture checks are useful but not a complete accessibility assessment.
- Clarify that a browser-readable proxy CSRF token is distinct from forbidden upstream credentials; reconcile the current wording before treating it as a testable security requirement (`docs/superpowers/specs/2026-11-05-clinic-application-design.md:226-229`). Review the stale photo-activation note against Tasks 14–17 in the write plan.
- Cross-device locale persistence, print/export, retention/deletion, consent revocation and numerous procedure/lab/stock/billing/admin writes remain unverified or explicitly deferred. Do not infer coverage from a read-only screen.

## Methodology and evidence improvements

1. Maintain a traceability matrix linking each original requirement and acceptance ID to the approved spec, plan task, implementation, evidence class and explicit status (`not planned`, `planned`, `fixture verified`, `site verified`, `UAT approved`, or `blocked`). Include owner and evidence date.
2. Resolve the conflicts above at their authoritative source, then update downstream plans and tests; retain decisions and exceptions instead of silently rewriting history.
3. Establish a reviewed Spec Kit constitution from already-approved project constraints, then adopt its per-feature `specify → clarify → plan → tasks → analyze` flow for bounded future work. Generate reviewer-owned requirements checklists without marking them approved merely because code exists.
4. Use `converge` only when its formal implementation prerequisites and artifacts exist; do not retrofit a passing result onto incomplete work. Keep the existing plan ledgers and their scope/limitations until an explicit migration is agreed.
5. Add reproducible CI gates for unit tests, typecheck, lint, both builds and browser suites, retaining separate intercepted and local fixture-proxy evidence. The previously observed unsharded fixture-proxy run hit the CSRF issuance cap; sharded passes do not establish an unsharded pass.
6. Establish a reviewable version-control baseline when the owner authorizes it. The repository had no commits at assessment time; untracked files cannot be meaningfully reviewed with an ordinary Git diff. No files were staged or committed by this audit.
7. Before any live data or write capability, require signed installed-site evidence, a verified access matrix and record scope, TLS and operational/privacy controls, and operation-specific negative and recovery tests. Synthetic data and local HTTP evaluation cannot substitute for these gates.

## Evidence limitations

The specification review was independent and document-focused. No installed Frappe/ERPNext contract, actual production authorization, clinical UAT or current end-to-end full-suite pass was verified as part of this report. Individual implementation changes were under active review at the time; earlier test results can become stale after edits. `Context7` returned an invalid API key; Spec Kit references above are its official documentation.
