# Owner staff management and doctor onboarding

## Goal

Give the clinic Owner a simpler way to manage Frappe staff accounts and onboard a doctor who can sign in and be booked in the React reception workspace. The Owner can assign multiple approved clinic roles to one account; staff use the existing workspace switcher. Frappe remains the source of truth for users, practitioner records, schedules, and permissions.

## Approach

Use a **guided, resumable setup** within Staff & roles: save account and roles, link or create a practitioner where applicable, set working hours, then send the native invitation. Show which steps are saved so the Owner can resume after an error without creating duplicate records. A single submit wizard would obscure partial success when invitation delivery fails; leaving practitioner setup in Desk would not meet the agreed onboarding scope.

## Owner workflow

1. View all accounts readable through the Owner’s native Frappe permissions, including existing users, in a live paginated list. Create an account, edit approved clinic roles, or enable or disable an eligible staff account; no roster enrollment is required. A React role edit submits only the requested approved role changes; it does not directly change unrelated roles or User Type. Let Frappe run its normal User save hooks, reread the account, and show the resulting roles and any additional changes Frappe made. Show privileged, externally managed when known, role-profile-managed, and other incompatible accounts as read-only in React and leave their advanced controls in Desk. Disable an account as a standalone action, then confirm both its saved status and the effect on sign-in; native session cleanup can commit during save.

   **Add ordinary staff:** Create Reception and Cashier accounts enabled with one or more approved native roles. Check the email against all native Users before insert, including disabled accounts, and handle an insert-time duplicate without changing the existing account. The Owner does not set a password or separately activate the account. Staff use native password setup; this create action does not send an invitation.
2. In **Add Doctor**, start with an existing eligible `Healthcare Practitioner` or create a disabled, unlinked one. Use native fields and validation, including the practitioner’s department. Never reassign a linked practitioner, silently disable a currently active profile, or create a login at this step. Resume saved drafts from native records, without roster enrollment.
3. Create and attach a disabled, practitioner-specific weekly schedule, or use existing suitable hours without changing other doctors’ schedules. Require the service unit Marley needs for booking and reuse the weekly preview. Don't invent booking rules or replace Frappe's availability calculation. Save a new schedule and its attachment together.
4. On **Finish setup**, validate the draft, create the enabled Doctor login, link the practitioner, and activate the prepared records in one transaction, only after verifying the installed native save hooks do not commit midway for this operation. If that cannot be established, keep Finish unavailable rather than exposing a partially activated account. No new login exists before Finish. After setup commits, offer **Send invitation** and report whether it was queued, failed, or could not be confirmed. Retry invitation without recreating the account; never automatically replay an uncertain Finish.

   For disabled draft hours, Finish publishes a fresh native schedule for the selected practitioner and leaves the source schedule disabled and untouched. This avoids changing anyone else's hours, even if a draft was shared. The old disabled schedule may remain as history; do not automatically delete it.

   The review confirms weekly hours, not that any particular appointment will stay available. Marley still applies native leave, availability exceptions, service-unit capacity, and existing appointments.

## Authorization and boundaries

The Owner uses a named Frappe account with the native `System Manager` role, assigned by a Frappe administrator outside this screen. Do not use the built-in `Administrator` account. Enable this React feature only when the authenticated user is in the verified Owner workspace (`MGR`) and currently holds `System Manager`; check both on the backend. Do not map `System Manager` to a second React workspace or automatically grant it to other Managers. Use native Frappe permission checks for each operation; `System Manager` is not a reason to bypass Marley permissions. Verify any additional permissions needed for practitioner and schedule setup on the installed site.

**Deployment default:** When a site administrator explicitly configures a named account as a Clinic Owner, the deployment setup provisions native `System Manager` and `Healthcare Administrator` roles plus dedicated `Healthcare Practitioner` permission to read, write, and create. The practitioner grant does not include delete, share, or unrelated DocType permissions; existing site grants are preserved. Running provisioning for one account must not grant Practitioner Create to previously configured Owners who were not selected. This is a permanent, repeatable site configuration, including production, not a temporary UAT grant. The stock Healthcare Administrator role grants broader Marley administration in Desk and covers schedules; its default grants do not cover practitioner writes on the pinned version. Do not add practitioner grants to the shared Healthcare Administrator role or assign a clinical role to the Owner. Do not grant these roles to users just because they map to or select the `MGR` workspace. Do not grant or restore privileges on sign-in or an ordinary application upgrade.

The list reads native `User` records directly; there is no separate membership roster. Any onboarding progress state tracks only unfinished setup and does not decide who can be listed or managed. Determine edit eligibility from fresh native permissions, account protections and the supported staff operations. Enforce the configured allowlist of assignable clinic roles on the backend. Do not expose a general User editor, grant Owner or broad administrator roles from this screen, or let the Owner edit their own roles or disable their own account here. Broader Frappe administration remains available in Desk under native permissions. Do not reuse the broad synthetic Reception role as an assignable production bundle or repurpose the legacy SIT-only admin write paths as production authority. Disabling a user controls sign-in; it does not deactivate the practitioner, change their schedule, or cancel appointments.

Do not merge either prior feature branch or deploy to production as part of this design. Owner onboarding depends on a build that includes the workspace switcher; end-to-end booking acceptance also requires the doctor-booking build.

## User acceptance

Use Playwright MCP on isolated synthetic SIT with fictional accounts, including a named Owner provisioned with the deployment defaults, not the built-in `Administrator`. As Owner, create a Reception + Cashier account and verify that staff can switch between workspaces. Onboard a fictional doctor, set working hours and verify the saved setup. As Reception, find the doctor, see those hours as bookable slots, and book an available appointment. Verify that neither a non-Owner nor a Manager without `System Manager` can open Staff & roles. When the Owner disables a managed account, verify the staff member's existing browser session and their ability to sign in again. Verify invitation delivery only through a synthetic mail sink; do not send real email. Report only what was observed through the UI. Implementing this provisioning default and testing it in SIT do not authorize applying it to an existing production site.
