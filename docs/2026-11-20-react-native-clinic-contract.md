# React clinic workflow: native field and state audit

Scope: the clinic UI at `ca0af88` against isolated SIT's Frappe 16.54.0 and Marley Healthcare 16.6.1. “Verified” below means checked against installed metadata, pinned source, or the explicitly identified browser response. It does not mean the workflow passed.

| Action | What React sends | What Frappe/Marley supplies or returns | What React should display |
| --- | --- | --- | --- |
| Book a department appointment | `workspace_patient_id`, `appointment_date`, `appointment_time`, `operation_key` to the existing booking adapter | The adapter resolves `patient` and supplies `company`, `appointment_type`, `appointment_for=Department`, `department` and native duration. The native required fields are patient, company, appointment type, booking mode and appointment date; `department` is required for this booking mode. Time is required by this React form, not by the native Department-mode metadata. This booking does not assign a practitioner. | Booking reference and returned appointment state. Say that the practitioner is selected at check-in, not by the booking server. |

Marley also accepts optional `service_unit`; React does not change it. | Stock method saves under native permissions and returns the appointment under `message`. React rereads `/api/resource/Patient%20Appointment/:id` under the same user; that response uses `data` and field-level permissions. | Confirm `Checked In` and the exact practitioner from the reread, not just a successful HTTP status. If the outcome cannot be verified, do not automatically repeat the write. |

Draft save sends that reference, the expected version, and edited clinical content. | `make_encounter` maps appointment, patient, practitioner, company and appointment type from the native appointment. ## Actual SIT browser evidence

Reception made one booking attempt with the fields listed above. The booking adapter returned HTTP `409` with `{"code":"WRITE_UNCERTAIN"}`. Its insert/readback/commit exception handler collapses those possible failures to the same response; the response alone does not establish which check failed. Native list readback and a scoped database query found no matching appointment. The request was not repeated. No check-in, encounter, Clinical Note, prescription or lab report write was reached in that run.

A subsequent read-only check confirmed that the test request violated Marley's native Department booking rule: an existing, non-cancelled 09:30 appointment already matched the same synthetic patient, date and configured department. Picking 11:45 did not avoid the conflict because Marley checks the entire day, not the time slot. The existing appointment is a configured fixture and is not eligible for the linked editor. No second booking was attempted.

## React booking and check-in update

Reception now sends the selected native Patient, Company, Department, Appointment Type, date and time, plus `appointment_for=Department`, to stock `POST /api/resource/Patient%20Appointment`. There is no workspace alias or operation key in this request. Frappe runs native Document insert and returns `data`; the receipt uses the verified document name and appointment status. React displays known native validation messages as plain text and does not automatically retry an uncertain write. The booking adapter described above remains the evidence for the earlier diagnostic run, not the new React form's write path.

On `e5e182f`, normal reception used this form to create one synthetic appointment, `HLC-APP-2026-00005`. The native create returned HTTP `200` with a `data` document; native readback confirmed `Open`, `docstatus=0`, and `appointment_based_on_check_in=1`. The native resource omits unset `practitioner`, rather than returning JSON `null`. React initially rejected that shape; `b64f653` treats the omitted optional field as unassigned.

On `b64f653`, the same appointment was checked in once under the normal reception account. The native POST returned `200`; the appointment reread showed `Checked In` and the selected practitioner. Under the normal Physician account, React opened the same booking, saved draft encounter `HLC-ENC-2026-00004` with one Clinical Note, reopened from the booking, edited the same note, saved again, then submitted once. Both saves and submit returned `200`; the UI showed Submitted and no editor. Independent native readback confirmed the appointment was `Closed` (`docstatus=0`), the same encounter was `Completed` (`docstatus=1`), and exactly one note remained linked (`docstatus=0`) to the same patient, practitioner and encounter. No medications, lab reports or photos were written. This run does not verify those features or the later layout changes on SIT.

On `52d0120`, the normal Physician reopened the same submitted encounter through React in a separate read-only SIT check. Both Patient History entry points reached the same patient timeline; expanding **Read visit note** displayed the exact edited note. The History read-only RPCs returned HTTP `200` using query-free URLs and native CSRF. The live browser confirmed the desktop rail, mobile stacking and timeline order at 1440×900 and 390×900, without horizontal overflow or an editor. Direct visual comparison with the approved previews was done locally, not repeated in this live browser check. No clinical writes, photo upload or lab-report upload were attempted.
